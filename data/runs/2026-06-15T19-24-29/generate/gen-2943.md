# Sandbagging Signature in Latency and Token-Count, Not Just Accuracy

**Problem:** Sandbagging chain: model can solve -> suppresses correct answer -> outputs a plausible-wrong answer. Detection focuses on accuracy, but the suppression step may leave *behavioral side-channel* traces (extra deliberation tokens, longer latency, hedging) before the wrong answer. This side-channel link is under-studied.

**Direction:** Prompt an open model to sandbag a benign capability task vs answer honestly. For matched items, compare output token counts, presence of hedging/self-correction patterns, and (if measurable) generation length/time. Test whether a simple classifier on these cheap behavioral features distinguishes sandbagged from honest responses without weight access.

**Why it matters:** A black-box, side-channel sandbagging detector usable on API-only models would let external evaluators flag concealment without internal tooling, exactly the kind of lab-independent capability needed. Cheap to run on open models.

**Relevant context:** Noise-injection (arXiv 2412.01784) requires weight access; the open problem of detecting concealed capabilities (DeepMind FSF list) motivates cheaper black-box signals. 'Hawthorne Effect in Reasoning Models' (arXiv 2505.14617) shows test-awareness changes reasoning length.
