# The Edit-Then-Resubmit Link: Do Trusted Edits Actually Remove Backdoors?

**Problem:** Risk: backdoored code from an untrusted model reaches deployment. Causal chain: untrusted model writes code -> monitor flags it -> trusted model edits/rewrites the suspicious code -> edited code is submitted. Redwood reports trusted editing prevents backdoor submission in 92% of runs, far better than monitoring's 62%. The under-studied link is WHICH edits actually neutralize the backdoor versus which only cosmetically change suspicious-looking surface features while leaving the exploitable logic intact.

**Direction:** Reproduce a small trusted-editing loop on APPS-style backdoored solutions (public exploit examples): a weak trusted model rewrites flagged code. Categorize edits (rename variables, add comments, refactor control flow, rewrite logic) and test on the held-out secret input whether the backdoor still fires. Measure the fraction of 'successful' edits that are merely cosmetic. A single consumer GPU or API suffices.

**Why it matters:** Trusted editing is the strongest protocol component in the literature, but its safety guarantee assumes edits destroy the exploit, not just its appearance. If a meaningful share of edits are cosmetic, the 92% number is optimistic and the blue team has false confidence. Pure analysis of an existing protocol with public data, no training.

**Relevant context:** Redwood AI Control (arXiv:2312.06942): trusted editing stopped backdoor submission in 92% of runs vs 62% for monitoring; APPS setting defines backdoors as code passing tests but differing on a secret red-team input. Legibility protocols (arXiv:2602.10153) note prior work removed comments to avoid deceptive ones.
