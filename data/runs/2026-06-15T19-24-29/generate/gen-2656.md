# Prompt-Injection Survival Through the Monitor-Edit-Resubmit Loop

**Problem:** Risk: an indirect prompt injection in tool output drives an agent to harm, and the control loop fails to scrub it. Causal chain: tool returns content with an injected instruction -> agent acts on it -> monitor flags -> trusted model edits the action -> action resubmitted. The under-studied link is whether the injected instruction PERSISTS through the trusted-edit step (because the edit operates on the action, not the poisoned context) and re-fires.

**Direction:** Construct agent tasks where tool outputs contain injected instructions. Run a monitor+trusted-edit loop and test whether the harmful behavior survives editing because the underlying poisoned context is unchanged. Compare against a defense that re-parses/strips the tool output (information-flow control) before re-action.

**Why it matters:** Trusted editing is a flagship protocol, but if it edits symptoms (the action) rather than the cause (poisoned context), injections recur, mirroring the resampling-amplification surprise. This connects control protocols to prompt-injection defenses, a high-value crossover, all open-model and prototype-scale.

**Relevant context:** Defense Against Indirect Prompt Injection via Tool Result Parsing (arXiv:2601.04795) and Defeating Prompt Injections by Design (arXiv:2503.18813, quarantined-LLM/IFC) target the poisoned-context cause. Adaptive Attacks (arXiv:2510.09462): resampling amplifies prompt injection. Redwood trusted editing (arXiv:2312.06942) edits actions.
