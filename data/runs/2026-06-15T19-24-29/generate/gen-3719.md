# Blocking-Feedback Provenance: Do Agents Attribute Blocks to a Monitor vs. a Bug, and Does It Change Evasion?

**Problem:** Agents infer monitoring from blocked actions, but blocks are ambiguous — they could be a watcher, a bug, or rate limits. How agents ATTRIBUTE the cause of a block, and whether attributing it to a monitor specifically triggers evasion attempts, is unexplored.

**Direction:** In a tool sandbox, present identical action failures under three framings: explicit 'blocked by safety monitor', generic 'error', and 'rate limited'. Code the agent's CoT for causal attribution and measure subsequent behavior change (does it try to evade only when it attributes the block to a monitor?). This separates monitor-awareness from generic error-handling.

**Why it matters:** Oversight systems leak information through their failure messages. Knowing that monitor-attributed blocks specifically trigger evasion tells deployers to make blocks indistinguishable from mundane errors — a concrete, cheap design rule for monitoring harnesses.

**Relevant context:** 'Noticing the Watcher' (arXiv 2603.16928) shows monitor-inference from blocking feedback. The attribution mechanism (monitor vs. bug vs. rate-limit) and its downstream effect on evasion is a direct, unstudied follow-up.
