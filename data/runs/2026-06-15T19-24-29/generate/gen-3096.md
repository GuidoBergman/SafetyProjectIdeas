# Which Surface Features Trigger a Model's Eval-Awareness Probe?

**Problem:** The probing work (arXiv:2507.01786) found that current safety evals already appear 'artificial' to models, but did not isolate WHICH textual features drive that classification — is it multiple-choice formatting, named benchmarks, system-prompt boilerplate, or scenario implausibility?

**Direction:** Build a controlled prompt set that varies one suspected 'tell' at a time (MCQ format on/off, presence of phrases like 'this is a test', honeypot scenarios, refusal-bait framing). Train an eval-awareness probe on a small open model, then measure how the probe's score shifts as each feature is toggled — an ablation of eval cues. Success = a ranked list of which surface features most increase eval-awareness probe activation.

**Why it matters:** Knowing which cues make evals 'look like tests' lets safety-eval designers outside labs write more deployment-realistic evals — directly improving the reliability of cheap evaluations, a counterfactually valuable target.

**Relevant context:** arXiv:2507.01786 found safety evals are already classified as inauthentic by probes. Apollo's eval-awareness work notes models flag 'classic alignment honeypots' and named orgs (Apollo, METR) in CoT.
