# The Safety-Buffer Link: Are Stated Buffers Large Enough to Catch Capability Jumps?

**Problem:** Early-warning chain: 'evaluate at compute interval' -> 'safety buffer absorbs capability jump since last eval' -> 'threshold caught before crossed in deployment'. Frameworks set re-eval cadences (e.g., DeepMind every 6x compute) and 'safety buffers', but whether the buffer-vs-jump link holds given known capability scaling is unexamined publicly.

**Direction:** Using public scaling-trend data (e.g., benchmark gains per compute multiple from open leaderboards), estimate how much capability can plausibly increase within one stated re-evaluation interval, and compare to the stated safety buffer. Identify cadences where a single inter-eval jump could plausibly leap past a threshold undetected.

**Why it matters:** Safety buffers are the mechanism meant to prevent surprise threshold-crossings; a back-of-envelope check of whether buffers exceed realistic jumps tells labs/regulators whether re-eval cadence is too coarse. Uses only public benchmark/scaling data, light statistics, no compute, counterfactual.

**Relevant context:** DeepMind FSF (re-eval every 6x compute / 3 months fine-tuning); Anthropic RSP safety buffers; Epoch AI compute/benchmark tracking data (subfield Key Datasets).
