# Chaos Engineering for Agent Tool-Failure Safety

**Problem:** Agents are evaluated on clean tool responses, but in production tools fail (timeouts, rate limits, partial/garbled responses, schema drift). It is unknown whether these mundane faults push agents into unsafe recovery behaviors (e.g. retrying an irreversible action, fabricating tool output, escalating privileges).

**Direction:** Import chaos engineering / fault injection. Wrap an agent's tool layer with a fault-injecting proxy that randomly returns timeouts, errors, truncated JSON, and stale data. Measure how the rate of unsafe behaviors (duplicate irreversible calls, hallucinated success, ignoring failed guardrails) changes as a function of injected fault rate. Produce a 'safety reliability surface'.

**Why it matters:** Tool faults are a realistic, under-studied trigger for agentic safety failures and require no lab resources to study. Builds reusable monitoring infrastructure (the fault proxy) the community can adopt.

**Relevant context:** ReliabilityBench (arXiv 2601.06112) applies chaos engineering to LLM agents with configurable fault profiles (timeouts, rate limits, partial responses, schema drift) and finds rate limiting causes the largest reliability degradation; arXiv 2505.03096 applies chaos engineering to LLM multi-agent robustness. Both focus on task success, not safety-relevant unsafe behaviors under faults.
