# A Post-Deployment Safety-Drift Canary: Detecting When an Updated Model Quietly Got Less Safe

**Problem:** GAP TARGETED: the under-researched subfield 'post-deployment safety monitoring' — open observability tools track latency/cost/toxicity drift but none provide a focused, statistically grounded canary for SAFETY regression (e.g., refusal rate silently dropping) across model versions or routing changes.

**Direction:** Build a small 'safety canary' harness: a fixed panel of ~150 probe prompts spanning refusal, sycophancy, and a few jailbreak templates. Define control-chart-style thresholds (e.g., CUSUM / EWMA on refusal rate) calibrated on a baseline model. Then simulate 'deployment drift' by swapping in a different/quantized/fine-tuned open model and show the canary fires when safety regresses, with controlled false-alarm rate.

**Why it matters:** Bridges ai_control + evaluations_benchmarks + adversarial_robustness. Post-deployment monitoring is named a clear ecosystem gap; this is the missing open prototype. Strongly counterfactual: a lab can A/B internally, but a public canary lets any deployer or auditor catch regressions with no lab access — and it is a self-contained, valuable tool on its own.

**Relevant context:** Landscape lists 'open-source production safety monitoring' as absent. Existing LLM observability tools (Phoenix, Langfuse, TruLens) do generic drift/toxicity but not calibrated safety-regression alarms. Statistical process control (CUSUM/EWMA control charts) is a standard, beginner-accessible monitoring technique.
