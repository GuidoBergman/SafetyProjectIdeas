# Mutation testing for safety evals: measuring whether your eval suite would catch an injected misbehavior

**Problem:** We trust safety eval suites without knowing their sensitivity — if a model were slightly more harmful, would the suite detect it? Eval suites have no analogue of test-coverage adequacy.

**Direction:** Borrow mutation testing from software QA. Create controlled 'mutant' model behaviors by lightly steering an open model toward more harmful/sycophantic outputs (via system prompt or a small activation steer), then check what fraction of these injected regressions the eval suite flags — the 'mutation kill rate'. A suite that passes mutants is inadequate. Report kill rates for popular open safety evals.

**Why it matters:** Provides a meta-evaluation of eval quality — a recognized gap ('evaluating the evaluations') — using a proven SE methodology. No training; steering done with prompts/steering vectors. Valuable to the whole open-eval ecosystem.

**Relevant context:** Grounded in mutation-testing-for-LLM literature (Meta ACH, arXiv 2501.12862) and landscape scorer-reliability gap. Source subfield: software testing (mutation testing). Target subfield: evaluations_benchmarks.
