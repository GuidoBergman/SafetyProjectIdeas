# Async Monitoring Latency: How Many Harmful Actions Land Before the Alarm?

**Problem:** Risk: monitoring runs asynchronously, so harm occurs before the monitor flags it. Causal chain: agent acts -> monitor scores the action with some latency -> if monitoring lags execution, the agent completes irreversible harm before the alert returns. The under-studied link is quantifying, for realistic agent trajectories, how many additional (potentially harmful) steps execute within a given monitor-latency window, and how much a cheap 'pause on high-risk action type' rule shrinks that exposure.

**Direction:** Replay agent trajectories (SHADE-Arena/CUA-SHADE) and simulate async monitoring with a configurable latency (in steps). For malign trajectories, measure how many harmful actions execute before the monitor's flag would arrive. Then add a synchronous hard-stop for a small set of high-risk action types and measure the reduction in pre-alarm harm.

**Why it matters:** Real deployments monitor asynchronously for throughput; the latency gap is a concrete, under-quantified control failure mode. A study + a cheap hybrid (async-monitor + sync-stop-on-risky-tools) rule is practical infrastructure-relevant work, no training, open benchmarks.

**Relevant context:** Async Control: Stress-testing Asynchronous Control Measures for LLM Agents (arXiv:2512.13526) studies exactly this asynchronous-monitoring gap. CUA-SHADE-Arena provides step-wise shell agent trajectories. Subfield open problem on minimum runtime controls including kill switches.
