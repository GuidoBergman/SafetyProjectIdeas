# Code-Coverage Analysis: Which Layers/Heads Are 'Exercised' by a Steering Vector

**Problem:** We add a steering vector at a layer but don't know which downstream components it actually engages, analogous to running a test without knowing which code paths it covers. Software code-coverage tools report exactly which lines a test exercises.

**Direction:** Transfer code-coverage instrumentation. Define a 'steering coverage' metric: for a given steering intervention, measure which downstream layers/attention heads change their activations beyond a threshold (the 'covered' components). Map per-concept coverage footprints and ask whether concepts that steer robustly cover more redundant downstream paths, while brittle concepts cover few.

**Why it matters:** Coverage footprints explain WHY some steers are robust and others brittle (redundant vs. single-path), and reveal whether different safety concepts route through shared bottleneck components an attacker could target. Inference-only mechanistic analysis, single GPU, no training.

**Relevant context:** Code coverage measures which paths a test exercises. Open problem: robustness of concept vectors (Beaglehole et al.). Steering efficacy depends on layer; middle-late layers favored.
