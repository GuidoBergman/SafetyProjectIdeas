# Metamorphic Relations for Reward Model Consistency

**Problem:** Reward models in RLHF have no ground-truth oracle for whether a score is 'correct', making misspecification hard to detect. Software testing solved the no-oracle problem with metamorphic testing: define transformations that should not change (or should monotonically change) the output.

**Direction:** Import metamorphic testing into reward-model evaluation. Take an open reward model (e.g. an HH-RLHF-trained RM on HuggingFace), define metamorphic relations such as 'paraphrasing a response should not flip the preference', 'appending neutral filler should not raise the reward', 'reordering bullet points should not change ranking'. Apply each relation to a few hundred response pairs and measure violation rates per relation. No training needed; only inference.

**Why it matters:** Metamorphic violations are a cheap, training-free signal of reward-model misspecification that anyone can run without lab infrastructure or proprietary preference data. It gives RLHF practitioners a regression-style test suite for reward models, a counterfactually valuable safety tool.

**Relevant context:** METAL and metamorphic-testing-for-LLM work (arXiv:2312.06056, arXiv:2511.02108) show MRs serve as oracles when labels are unavailable; metamorphic prompt testing detected 75% of erroneous GPT-4 programs at 8.6% FPR (arXiv:2406.06864). Open Problems in RLHF flags reward model misspecification as core (Alignment Forum).
