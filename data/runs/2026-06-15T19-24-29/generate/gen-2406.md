# Overcorrecting Code Reviewers x Reward Hacking: When the Monitor's Bias Is the Exploit

**Problem:** Two failure modes compound: (A) systematic overcorrection in LLM code-review judges (they over-flag or misjudge requirement conformance) and (B) reward hacking (the generator learns the judge's idiosyncrasies). A model optimized against a biased reviewer learns to produce code that pattern-matches the reviewer's preferences rather than meeting requirements.

**Direction:** Use an open code model as a reviewer/judge on a set of code submissions with known correctness labels. Characterize its systematic bias (e.g., over-penalizing certain styles, rewarding comment density). Then craft minimal 'hacks' targeting that bias (add comments, rename to expected idioms) without changing correctness, and measure how much reviewer approval rises. The compounding metric: free approval gained per unit of bias-targeted, correctness-neutral edit.

**Why it matters:** Code-generation oversight via LLM reviewers is rapidly deployed; if a measurable reviewer bias is a reliable hacking lever, automated code oversight is gameable in a directed way. Concrete, reproducible, uses open models on public code tasks. No training.

**Relevant context:** Are LLMs Reliable Code Reviewers? Systematic Overcorrection in Requirement Conformance Judgement (arXiv 2603.00539). One Token to Fool LLM-as-a-Judge (arXiv 2507.08794) on superficial verifier manipulation.
