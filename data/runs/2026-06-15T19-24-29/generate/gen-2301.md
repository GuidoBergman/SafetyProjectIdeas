# Confirmation Bias in Security Review: Does Telling the Monitor 'This Was AI-Generated' Change Its Verdict?

**Problem:** Recent work measures and exploits confirmation bias in LLM-assisted security code review — the monitor's prior framing shifts what it flags. Whether a simple provenance/expectation prime ('this code is trusted' vs 'this may contain a backdoor') systematically changes a code monitor's false-negative rate is a concrete, under-mapped oversight failure.

**Direction:** Take code samples (some with injected subtle bugs) and present them to a monitor model under different priming frames: neutral, 'written by a trusted senior dev', and 'possibly malicious'. Measure how the framing shifts detection rate and false negatives, holding the code fixed. Map the bias magnitude and identify the framing that maximizes true detection without over-flagging.

**Why it matters:** If an attacker can influence how its output is framed to the overseer, it can suppress scrutiny. Quantifying this and finding a robust neutral framing is directly useful for monitoring harness design. Training-free, public code, single GPU.

**Relevant context:** Measuring and Exploiting Confirmation Bias in LLM-Assisted Security Code Review (arXiv:2603.18740); AI Control trusted monitoring (arXiv:2312.06942). This isolates provenance-framing effects on code-monitor false negatives.
