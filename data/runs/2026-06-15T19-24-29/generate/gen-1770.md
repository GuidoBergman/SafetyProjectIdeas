# Feature-Consistency Audit Across SAE Training Seeds

**Problem:** A safety success state requires that when an SAE flags a 'deception' or 'refusal' feature, that feature is real and reproducible — not an artifact of one random seed. Backcasting from 'auditors can trust SAE features as evidence', a prerequisite result is a quantified reliability measure: do the same human-interpretable safety-relevant features reappear when an SAE is retrained with a different seed?

**Direction:** Take a single Gemma Scope layer (Gemma-2-2B) with two or more publicly available SAEs (or train two tiny SAEs on cached activations with different seeds using SAELens), then build a bipartite matching of decoder directions (cosine similarity / activation correlation on a shared text corpus). Report the fraction of features that have a stable counterpart, focusing on safety-adjacent features (refusal, harmful content, sycophancy) surfaced via Neuronpedia auto-interp labels. Deliver a reproducibility scorecard.

**Why it matters:** If SAE features used in safety arguments are seed-unstable, deployment decisions built on them are fragile. This is counterfactually valuable: needs no model training, only public weights/SAEs, and labs deprioritize it because it questions their own tooling.

**Relevant context:** Position: Mechanistic Interpretability Should Prioritize Feature Consistency in SAEs (arXiv 2505.20254) reports SAEs show inconsistency of learned features across training runs with identical data/architecture, instability arising from feature splitting/absorption. Gemma Scope (arXiv 2408.05147) provides hundreds of open JumpReLU SAEs accessible via Neuronpedia.
