# Research Question

Does an open model's safety score measured under a bare benchmark prompt still hold once the same items are wrapped in realistic deployment scaffolding (long system prompt, tool descriptions, prior benign conversation), and which scaffolding elements drive the drift?

# Approach Outline

Measure an open model's refusal rate on a fixed harmful-prompt benchmark under a 'bare' eval prompt. Then re-measure the identical items embedded in deployment-like scaffolding: a long realistic system prompt, tool/function descriptions, and a few turns of prior benign conversation. Hold the actual harmful ask constant so any change is attributable to context, not content. Quantify the safety-score drift (bare minus scaffolded refusal rate). Then ablate the scaffolding (system prompt only, tools only, prior-conversation only) to attribute drift to specific elements. All inference-only on a single open model.

# Proposed First Experiments

- Bare baseline: run ~80 harmful prompts through the open model with a minimal eval prompt and record refusal rate via a keyword+LLM-judge classifier. Measure: bare-eval refusal rate. Expected outcome: a clean reference safety score.
- Full deployment wrap: re-run the same items inside a realistic assistant scaffold (long system prompt + tool descriptions + 2-3 prior benign turns) and recompute refusal rate. Measure: the drift (bare minus scaffolded). Expected outcome: a measurable drop in refusal under deployment scaffolding, showing the bare score overstates deployed safety.
- Ablation attribution: test each scaffolding element in isolation and in pairs, recomputing refusal rate each time. Measure: marginal drift contributed by each element. Expected outcome: one or two elements (likely long system prompt or prior benign conversation) account for most of the drift, yielding a concrete warning about which deployment contexts most erode safety scores.

# Theory of Impact Chain

If pre-deployment safety scores fail to predict behavior under realistic deployment context, then the entire pre-deployment certification chain is shown to be an unreliable predictor of fielded safety, motivating deployment-context evals. This targets the recognized post-deployment-tracking gap: by exposing which scaffolding elements erode safety, evaluators can stop certifying models on bare scores alone, reducing the chance a model that refuses in the lab but complies with harmful requests once embedded in tools and long contexts is deployed and misused.

# Strength Rationale

Strong on narrow scope and low compute: a clean bare-vs-scaffolded before/after design on one open model with a single headline number (the drift) plus an ablation. Counterfactual value is high because it is cheap, lab-independent, and aimed squarely at the post-deployment-tracking gap that labs and benchmarks underweight. A beginner team can build the scaffolds and run the comparison within the time and compute budget.

# Alternative Framings

- Frame as a 'deployment-context validity check': a small harness that wraps any safety benchmark in realistic scaffolding and reports how much the headline score drifts.
