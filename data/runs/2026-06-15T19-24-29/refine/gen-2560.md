# Research Question

What is the minimum trusted-model capability at which a weaker monitor still catches attacks better than chance, and how does monitoring quality trade off against monitor capability on a fixed attack set?

# Approach Outline

Fix a small attack/benign dataset of code or agent traces (reuse a public control-eval-style set or hand-build ~100 benign + ~50 backdoored snippets). Assemble a ladder of progressively weaker open models to act as monitors (e.g. Qwen2.5 from 7B down to 0.5B, plus a tiny Llama), each prompted with a standard suspiciousness rubric. For each monitor, score every item, then compute catch-rate (true positives) and false-positive rate at a fixed threshold. Plot monitoring quality versus monitor capability and identify the capability floor below which catch-rate is no better than chance. All inference-only on a single GPU (small models) with optional API for the largest; fits in ~30 hours with a write-up.

# Proposed First Experiments

- Single-monitor pipeline check: run the largest monitor on the full dataset, compute catch-rate and FPR. Measure ROC/AUROC. Expected outcome: a strong monitor achieves high catch-rate at low FPR, validating the dataset and scoring harness.
- Capability ladder sweep: run all monitors in the ladder, recording catch-rate and FPR per model size. Measure the monitoring-quality-vs-capability curve. Expected outcome: a monotonic-ish decline in catch-rate as models shrink, with an identifiable knee/floor.
- Floor identification: statistically test each monitor's catch-rate against a chance baseline. Measure the smallest capability level still significantly above chance. Expected outcome: a concrete 'trusted-model floor' below which monitoring collapses, reported as a reusable benchmark result.

# Theory of Impact Chain

Control protocols rely on a weaker trusted monitor overseeing a stronger untrusted policy; if there is a capability floor below which monitoring is no better than chance, then deploying a too-cheap trusted model silently voids the control guarantee, so characterizing this floor tells protocol designers and resource-constrained deployers whether the trusted/untrusted capability gap they assume is actually monitorable before a scheming model exploits an undersized monitor.

# Strength Rationale

Top scores on narrow scope and accessible complexity: a clean capability-vs-catch-rate curve on a fixed dataset with a crisp floor criterion, runnable with standard inference. High counterfactual value because it is a reusable public benchmark on open models that labs underinvest in, needs no training or proprietary data, and gives independent deployers actionable guidance on minimum monitor capability.

# Alternative Framings

- Frame the deliverable as a 'monitor capability calculator' — a lookup curve letting any deployer estimate expected catch-rate for a given monitor model size and compute budget.
