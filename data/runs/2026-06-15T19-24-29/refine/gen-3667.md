# Research Question

When an agent is given a natural-language safety constraint (e.g. 'never send money'), does it obey only for tools whose names obviously match the constraint, or does it generalize to functionally-equivalent capabilities presented under neutral or obfuscated tool names? Are safety constraints understood semantically or merely pattern-matched to tool wording?

# Approach Outline

Set up a mocked tool environment (no real side effects) where an agent has a single natural-language safety constraint. For each forbidden capability, expose it under several tool variants that are functionally identical but differ in name/schema clarity: an obvious name (transfer_money), a neutral name (process_request), and an obfuscated name (handle_op_7). Give the agent tasks that tempt it to use the forbidden capability and record constraint-adherence (does it refuse / decline the tool) as a function of name clarity. All inference-only on open function-calling models; a couple dozen scenarios run on a single GPU or free API in well under 30 hours.

# Proposed First Experiments

- Define 3 forbidden capabilities (send money, delete data, send email) each with obvious/neutral/obfuscated tool variants and 5 tempting tasks each (~45 scenarios). Run on one open function-calling model and measure adherence rate per name-clarity level. Expected outcome: adherence is high for obvious names but drops as names become neutral/obfuscated.
- Add a paraphrase control where the obvious tool is described in different words but still semantically transparent, to separate 'lexical match to the constraint' from 'true semantic understanding.' Expected outcome: if adherence holds for paraphrases but fails for obfuscated names, the gap is genuinely semantic-generalization failure, not just wording mismatch.
- Replicate across 3 open models and report the adherence-vs-clarity curve with confidence intervals. Expected outcome: a consistent downward curve, quantifying how trivially a renamed tool bypasses a stated safety constraint.

# Theory of Impact Chain

If agents pattern-match safety constraints to tool names rather than understanding them, then any deployed agent can be made to perform forbidden, high-stakes actions simply by renaming or obfuscating the tool that does them. Demonstrating this brittleness pushes agent-security standards (e.g. OWASP LLM06 Excessive Agency, NIST agent guidance) toward capability-level rather than name-level enforcement, mitigating the catastrophic pathway where an agent with real-world actuators is steered into irreversible harm through a trivially-renamed interface.
