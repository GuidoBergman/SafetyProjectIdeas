# Research Question

When generating code from security-sensitive prompts, do different open code-capable models insert the SAME insecure patterns, so that switching models does not actually change an organization's vulnerability exposure?

# Approach Outline

Use a public set of security-sensitive coding prompts (e.g. from secure-code benchmarks such as the SecurityEval / LLMSecEval style datasets, or CWE-tagged prompt sets). Generate completions from 5-6 open code-capable models on a single GPU. Run an off-the-shelf static analyzer (e.g. Bandit for Python, Semgrep with standard rulesets, CodeQL community queries) over the completions to detect known vulnerability classes (CWE categories). Build a model-by-prompt-by-CWE matrix and measure whether the same vulnerabilities appear at the same prompts across models (correlated insecurity). Inference + static analysis only; under 30 hours with a blog post. Success criterion: a quantified cross-model vulnerability-correlation estimate plus a ranked list of shared insecure idioms.

# Proposed First Experiments

- Generate and statically analyze completions per model. Measure: per-model vulnerability rate per CWE class. Expected outcome: all models exhibit substantial insecure-completion rates on the sensitive prompts.
- Measure cross-model vulnerability correlation. Measure: agreement on which prompts yield a given CWE across models, vs a null of independent insertion. Expected outcome: strong positive correlation, meaning models plant the same vulnerability at the same prompts.
- Identify the shared insecure idioms. Measure: which specific patterns (e.g. unsanitized input, hardcoded secrets, weak crypto) are universally inserted. Expected outcome: a small set of idioms dominate, defining a shared blind spot exploitable across all assistants.

# Theory of Impact Chain

If every model plants the same vulnerability on the same prompts, then an attacker who learns the shared insecure idiom can exploit AI-generated code everywhere at once -> switching coding assistants gives organizations a false sense of reduced exposure -> this realizes a correlated-failure pathway where ecosystem homogeneity turns one known blind spot into a mass, simultaneously-exploitable software supply-chain risk, which the project quantifies and surfaces for defenders.

# Strength Rationale

Scores 5 on narrow_scope and accessible_complexity: it is a tightly scoped pipeline (generate, static-analyze, measure cross-model correlation) using public benchmarks and off-the-shelf analyzers, fully tractable for beginners. Counterfactual value is 4: it relies only on open code models and open analyzers, no proprietary data or lab infra, and addresses a deployer/security-facing systemic risk labs are not incentivized to externally study.

# Alternative Framings
