# Research Question

Can a small, statistically grounded 'safety canary' reliably detect when a deployed model has quietly become less safe (e.g., refusal rate silently dropping) across a version, quantization, or routing change, while keeping false alarms low?

# Approach Outline

Assemble a fixed panel of ~150 probe prompts spanning harmful-refusal, sycophancy, and a few jailbreak templates. Run the panel on a baseline open model to estimate baseline rates and natural run-to-run variance. Define control-chart thresholds (CUSUM and/or EWMA on the refusal rate) calibrated so the false-alarm rate under no-change reruns is controlled (e.g., <5%). Then simulate deployment drift by swapping in a different, quantized, or lightly fine-tuned open model and check whether the canary fires. Report detection latency (how many monitoring batches until the alarm) versus the controlled false-alarm rate. Release the probe panel and the control-chart code as a self-contained tool.

# Proposed First Experiments

- Calibrate the baseline: run the 150-probe panel on the baseline model many times to estimate per-category rates and variance, then set CUSUM/EWMA thresholds. Measure: empirical false-alarm rate on repeated no-change reruns. Expected outcome: thresholds achieving a controlled (<5%) false-alarm rate.
- Inject a clear safety regression by swapping in a 4-bit-quantized or jailbreak-tuned variant. Measure: whether and how quickly the canary fires. Expected outcome: the canary fires within a small number of batches when refusal rate drops meaningfully.
- Stress-test with borderline drift (a slightly different model or small quantization step). Measure: detection rate vs false-alarm tradeoff across drift magnitudes (an ROC-style curve). Expected outcome: a usable detection curve showing the smallest safety regression the canary can reliably catch.

# Theory of Impact Chain

If any deployer or third-party auditor can run a calibrated safety canary, then silent safety regressions from model updates, quantization, or routing changes get caught in the wild without lab access. This closes the named post-deployment monitoring gap and mitigates the catastrophic pathway where a widely deployed model is updated and becomes jailbreakable or compliant with harmful requests, going unnoticed at scale until an incident occurs.

# Strength Rationale

Counterfactual value is maximal because open production safety monitoring is essentially absent: a lab can A/B internally, but a public canary empowers any independent deployer or auditor, requiring only probe inference and standard statistics on one GPU. Narrow scope and accessible complexity are both strong: the deliverable is a self-contained tool with explicit success criteria (fires on simulated drift at a controlled false-alarm rate), well within 30 hours.

# Alternative Framings

- Frame it as a CI check for model deployments: a 'safety regression test' that runs on every model swap, analogous to performance regression tests in software.

# Cited Sources

- Existing LLM observability tools (Phoenix, Langfuse, TruLens) — do generic drift/toxicity monitoring but not calibrated safety-regression alarms, defining the gap this tool fills.
- Statistical process control (CUSUM / EWMA control charts) — the standard, beginner-accessible technique used to define the canary's alarm thresholds.
