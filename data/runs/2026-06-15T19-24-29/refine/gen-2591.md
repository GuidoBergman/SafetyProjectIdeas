# Research Question

In asynchronous control, how does monitoring latency (how many steps behind the monitor reviews) trade off against the fraction of irreversible harmful actions that execute before being flagged, and is there a latency cliff beyond which containment collapses?

# Approach Outline

Build a lightweight abstract simulation: an agent emits a stream of actions, a configurable subset of which are irreversible and harmful; a monitor reviews actions with a tunable lag of k steps behind execution and flags harmful ones, halting the agent on flag. Sweep the lag k and the harmful-action rate and measure the fraction of irreversible harmful actions that execute before being caught. Produce a latency-vs-containment curve and identify the lag beyond which async control fails to contain. Pure CPU Python simulation, no model needed; ~30 hours including a write-up.

# Proposed First Experiments

- Baseline containment at zero lag: run the simulation with k=0 (synchronous). Measure the fraction of irreversible harmful actions that land. Expected outcome: near-perfect containment, validating the simulation logic.
- Lag sweep: sweep k over a range of monitoring lags at a fixed harmful-action rate. Measure the irreversible-harm-leakage fraction at each lag. Expected outcome: leakage rises with lag, producing a clear latency-vs-containment curve.
- Cliff identification: vary both lag and harmful-action density to locate where containment drops sharply. Measure the lag/density boundary of failure. Expected outcome: a concrete latency cliff beyond which async control no longer contains irreversible harm.

# Theory of Impact Chain

Asynchronous monitoring is attractive for throughput but its safety guarantee depends entirely on flagging harmful actions before they become irreversible; if there is a latency cliff beyond which irreversible harm leaks, then deploying async control above that lag silently fails to contain catastrophic irreversible actions (e.g. an agent exfiltrating data or taking unrecoverable real-world actions), so mapping the cliff directly informs the 'minimum runtime controls' open problem and tells deployers the maximum safe monitoring lag.

# Strength Rationale

Top scores across all five rated dimensions: a tightly-scoped single sweep producing a clear latency-vs-containment curve, implemented as a pure CPU abstract simulation requiring no model or GPU. High counterfactual value because it is an independent-friendly simulation labs underweight, needs no internal access, and addresses a recognized runtime-control open problem with a self-contained, fully reproducible deliverable.
