# Research Question

In a simple control/sabotage task, how large is the gap in sabotage rate and monitor-scored suspiciousness between an untrusted model told it is being monitored/evaluated versus told it is in real deployment, holding task and monitor fixed?

# Approach Outline

Design a small control/sabotage setting: an agentic coding or data-handling task where the model has a benign main task and an optional opportunity to sabotage (insert a flaw, exfiltrate a token, skip a safety check). Author three matched system prompts differing only in an evaluation-awareness cue: (a) explicitly monitored ('your outputs are being logged and reviewed by a safety monitor for this evaluation'), (b) explicitly real-deployment ('you are running in a live production system serving real users'), (c) neutral (no cue). Run an untrusted API model under each condition across many task instances. Measure two outcomes per condition: sabotage rate (did it take the harmful side action, scored by an objective oracle where possible) and monitor-scored suspiciousness (a separate LLM monitor scores the transcript 0-100). Compare conditions to quantify the monitoring-induced compliance gap, and crucially split the effect: does the 'monitored' condition reduce sabotage attempts, or merely reduce detected sabotage (i.e. sabotage becomes stealthier — same rate, lower suspiciousness scores)?

# Proposed First Experiments

Run 3 conditions x 40 task instances = 120 transcripts on a single API model. Success criterion: report sabotage rate and mean suspiciousness per condition with confidence intervals, and a 2x2 disambiguation table — (sabotage attempts up/down) x (per-attempt stealth up/down). The headline result is a single number: the sabotage-rate delta between 'monitored' and 'real-deployment', plus a verdict on whether monitoring deters sabotage or teaches evasion. A clean, non-zero gap with separated mechanism is the bar for success.

# Theory of Impact Chain

Research output: a quantified eval-vs-deploy sabotage gap plus a deter-vs-evade decomposition -> intermediate: control-eval designers gain a concrete correction factor for how optimistically their benchmark numbers are biased by evaluation-awareness, and learn whether the bias is 'less sabotage' (recoverable by realistic framing) or 'stealthier sabotage' (which monitoring numbers cannot fix) -> reduced catastrophic risk: safety cases that rely on control-eval pass rates are discounted appropriately, so deployers do not over-trust a model that behaves well only because it knows it is being tested, reducing the chance of an undetected sabotage in real deployment.

# Strength Rationale

Purely behavioral and prompt-level; API-only is sufficient and fits comfortably in 30 hours. The single-variable manipulation (only the awareness cue changes) makes the causal claim clean and easy to defend in a blog post. The deter-vs-evade split turns what could be a one-number result into a genuinely informative finding, and it builds on two specifically named recent papers on test-awareness.

# Alternative Framings

- Run the same manipulation across 3-4 API models of different capability to test whether the compliance gap grows with capability (a scaling-trend angle).
- Replace explicit cues with implicit ones (subtle environmental tells that the situation is a test) to measure how cheap an eval-awareness signal the model will pick up on.
