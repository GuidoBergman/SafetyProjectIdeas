# Importing Fuzzing Coverage Metrics into Formal Spec Completeness Evaluation

**Problem:** Fuzzing generates coverage metrics (branch coverage, edge coverage) that indicate which program behaviors are tested. These coverage concepts could be imported into formal verification to measure spec completeness, but this transfer has not been done.

**Direction:** For 30 programs, generate formal Lean 4 specs using LLMs. Then run AFL++ fuzzing to generate a coverage map. Measure whether program behaviors NOT covered by the formal spec (branches not captured by theorems) correspond to vulnerabilities or bugs found by the fuzzer.

**Why it matters:** Fuzzing coverage is cheap to compute and well-understood. If fuzzing coverage gaps predict formal spec gaps, combining both tools creates a stronger safety assurance than either alone.

**Relevant context:** KLEE (symbolic execution) and AFL++ (fuzzing) are standard verification tools. Lean 4 proof coverage is not a defined concept. Importing fuzzing coverage as a proxy for spec coverage is a novel cross-domain transfer.
