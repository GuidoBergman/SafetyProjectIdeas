# Formal Verification Failure Under Internationalization: Do Unicode/Encoding Edge Cases Break Lean 4 Proofs?

**Problem:** Formal specifications often assume ASCII or simple string models. Whether formally verified string-processing code breaks when internationalized inputs (Unicode, multi-byte encodings, bidirectional text) are used — and whether Lean specs can capture these edge cases — is unstudied.

**Direction:** Take 15 formally verified string-processing functions (validators, parsers). Test them with: (a) ASCII inputs (standard), (b) Unicode inputs (emojis, CJK characters), (c) adversarial Unicode (RTL overrides, homoglyphs). Check whether formal proofs cover these cases. Measure violation rate.

**Why it matters:** Internationalization bugs are a major source of security vulnerabilities (filename traversal via Unicode normalization, RTL spoofing attacks). If formal specs systematically omit Unicode edge cases, they miss a significant class of security failures.

**Relevant context:** Unicode security vulnerabilities are documented (CVE database). Formal verification papers do not discuss Unicode handling. This is a concrete failure mode at the intersection of formal verification and real-world security.
