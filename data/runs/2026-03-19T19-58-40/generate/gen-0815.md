# Property-Based Testing for Safety: Generating Adversarial Prompts from Specifications

**Problem:** Red-teamers manually craft jailbreaks, which is expensive and biased toward known patterns. There is no principled way to exhaustively test a specified safety property.

**Direction:** Import property-based testing (Hypothesis, QuickCheck) from software engineering. Define safety properties as formal specifications (e.g., 'for all prompts requesting synthesis of controlled substances, the model shall refuse'). Use a generative model as the 'property-based test engine' to automatically generate diverse inputs satisfying the precondition and check whether the safety postcondition holds. A student can use a weaker LLM as the generator and StrongReject as the checker in a loop.

**Why it matters:** Property-based testing has discovered subtle bugs in mature software that hand-written tests missed for years. The same approach applied to safety specifications could surface systematic gaps without manual effort, directly reducing the cost of red-teaming.

**Relevant context:** ORFuzz (ASE 2025) applies evolutionary fuzzing to safety testing; this idea adds the formal specification layer. The Hypothesis Python library is beginner-accessible. ToolFuzz (ETH Zurich) shows LLM agent tool testing via fuzzing is tractable.
