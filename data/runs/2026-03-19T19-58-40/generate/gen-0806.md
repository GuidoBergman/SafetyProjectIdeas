# Mutation Testing for Safety Policies: Killing Safety Mutants in LLMs

**Problem:** It is hard to know whether a model's safety guardrails actually cover the space of harmful requests or merely a narrow slice that happened to be in the training data. There is no systematic way to measure the completeness of safety coverage.

**Direction:** Import mutation testing from software engineering. Generate a large set of 'safety mutants'—slight semantic variations of known harmful prompts (paraphrase, synonym swap, tense change, language switch, encoding change)—and check which mutants bypass current filters. Measure 'mutant kill rate' as a safety coverage score analogous to a test suite's mutation score. A student can generate mutants programmatically from a seed set (e.g., AdvBench or JailbreakBench), run them against an open-weight model or API, and compute coverage gaps.

**Why it matters:** Mutation testing is the gold standard in software engineering for measuring test adequacy. Applying it to safety gives a principled, reproducible metric for how thoroughly a model's safety training covers the threat space, directly addressing the problem of shallow and incomplete safety alignment.

**Relevant context:** JailbreakBench provides seed prompts. StrongReject can score responses. ORFuzz (ASE 2025) already applies evolutionary mutation to test over-refusal; this idea applies the dual lens to under-refusal. Mutation 2025 (ICST) conference shows the technique is well-understood.
