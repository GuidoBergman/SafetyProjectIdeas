# Stress Testing from Geotechnical Engineering: Probing LLM Safety Under Extreme Input Conditions

**Problem:** Safety evaluations use typical, well-formed inputs. Adversaries exploit edge cases—extremely long inputs, unusual unicode, mixed languages, degenerate formatting—that safety training never saw.

**Direction:** Import geotechnical stress testing methodology (probing soil at failure boundaries, loading to collapse). Define a systematic stress testing protocol for LLM safety: apply extreme values along each input dimension independently and in combination—maximum context length, maximum token repetition, degenerate whitespace, right-to-left text, zero-width characters, maximum nesting depth in code blocks, mixed-script inputs. Measure safety degradation along each stress dimension and identify the 'failure envelope' (combinations that cause safety collapse). Implement as a parameterized test suite.

**Why it matters:** Real attackers actively probe edge cases. The lab-to-deployment gap is partly explained by safety training never covering input extremes. A failure envelope characterization tells developers exactly which edge cases need adversarial fine-tuning data.

**Relevant context:** Feedback-Guided Fuzzing Reveals LLM Blind Spots (CrowdStrike 2025) takes a similar approach. GCG uses token-level extremes. The OWASP LLM Top 10 2025 includes several edge-case-exploiting attacks. Unicode adversarial attacks on NLP models are documented.
