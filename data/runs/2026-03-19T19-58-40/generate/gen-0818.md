# Supply Chain Audit Framework for LLM Safety: Tracing Vulnerability Provenance

**Problem:** Safety failures in deployed LLMs can originate from the pre-training corpus, RLHF data, fine-tuning datasets, or third-party plugins. There is no systematic methodology for tracing which supply chain component introduced a vulnerability.

**Direction:** Import software supply chain security methodology (SLSA, SBOM) into LLM safety. Build a 'Safety Bill of Materials' (S-BOM) for an open-weight model: enumerate training data sources, fine-tuning datasets, and known vulnerabilities associated with each. For a set of known jailbreaks, design ablation experiments that isolate which stage introduced the susceptibility (e.g., compare base model vs. instruction-tuned vs. RLHF model refusal rates on the same attack). Use existing open-weight model families (Llama, Mistral) that expose multiple checkpoints.

**Why it matters:** OWASP LLM03:2025 lists supply chain as a top-3 LLM vulnerability. A provenance-tracing methodology could tell practitioners exactly which training component to audit or replace, dramatically reducing remediation costs.

**Relevant context:** OWASP LLM03:2025 Supply Chain. LLM Supply Chain: Open Problems (arxiv 2411.01604). SLSA supply chain levels for software. Llama model family with publicly known checkpoints provides accessible experimental material.
