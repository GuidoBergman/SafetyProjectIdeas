# Code Coverage Metrics for Safety: Measuring Which Model Components Participate in Refusals

**Problem:** It is unknown whether safety-relevant computations are distributed across the model or concentrated in a few layers/heads. Concentrated safety is fragile; distributed safety is more robust.

**Direction:** Import code coverage analysis from software testing. Define 'safety coverage' as the fraction of model components (attention heads, MLP neurons, layers) that exhibit different activation patterns on refused vs. complied-with harmful prompts. Use gradient-based saliency or attention rollout to identify which components are 'exercised' during refusals. Measure whether jailbroken variants of the same prompt deactivate the same components. Test whether prompts with wider component coverage are harder to jailbreak.

**Why it matters:** Software engineers have long known that code with low test coverage is fragile. The analogous insight for LLMs would mean that safety concentrated in few model components is much more vulnerable to targeted attacks—motivating training strategies that distribute safety computation.

**Relevant context:** Activation probing is a listed methodology for this subfield. 'Safety Alignment Should Be Made More Than Just a Few Tokens Deep' (ICLR 2025) motivates depth-of-safety analysis. AISafetyLab provides hooks for activation analysis.
