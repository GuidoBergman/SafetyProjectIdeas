# Research Question

Among the real-world tools and approaches available today for LLM-assisted vulnerability discovery, which are most effective at finding known vulnerabilities in open-source C/C++ code? Specifically: how do existing security skills (Trail of Bits' Claude Code skills, Google's oss-fuzz-gen), the Anthropic-style file prioritization strategy, and a custom composite approach compare when evaluated against known CVEs in OSS-Fuzz projects — all using the same underlying model (Claude Opus 4.6)?

# Approach Outline

Benchmark existing, publicly available LLM security tools and scaffolding approaches against known CVEs in OSS-Fuzz C/C++ projects. All approaches use Claude Opus 4.6 as the underlying model, isolating the effect of the tool/scaffolding layer.

**Approaches to compare:**

1. **Trail of Bits `static-analysis` skill** (existing): Runs Semgrep and/or CodeQL analysis via Claude Code. Install from `trailofbits/skills` marketplace. This represents the current state-of-the-art in open-source, skill-based static analysis scaffolding for LLMs.

2. **Trail of Bits `variant-analysis` skill** (existing): Pattern-based vulnerability discovery — given a known vulnerability as a seed example, searches for similar patterns across the codebase. Tests whether example-guided search outperforms undirected analysis.

3. **Trail of Bits `audit-context-building` skill** (existing): Builds deep architectural context through ultra-granular code analysis before vulnerability hunting. Tests whether deep context-building improves discovery rates.

4. **Google oss-fuzz-gen** (existing): LLM generates fuzz targets, compiles them, runs with ASan (AddressSanitizer — a compiler flag that detects memory errors at runtime with zero false positives), and reports crashes. Extended with a Claude Code CLI backend class (~50-100 lines Python wrapping `claude -p` as subprocess). This represents the automated fuzzing approach.

5. **File prioritization (Anthropic-style)** (custom): Two-stage approach inspired by Anthropic's Mythos research — first pass has the LLM rank source files 1-5 by vulnerability likelihood, second pass focuses analysis only on top-ranked files. Implemented as a Claude Code skill or thin wrapper script.

6. **Custom composite** (custom): Ivan combines the most promising elements from the above approaches. For example: audit-context-building → file prioritization → static-analysis on prioritized files. Tests whether composing tools yields better results than any individual tool.

**Ground truth**: Select 10-15 OSS-Fuzz projects with well-documented CVEs. Build a map of {project, file, CVE-ID, bug class, severity} as the answer key.

**Verification**: ASan as crash oracle for fuzzing-based approaches. For static-analysis-based approaches, check whether the LLM identifies the known vulnerable code location and bug class.

**Tiered severity classification** (following Anthropic's Mythos framework):
- Tier 1: Any crash (ASan report)
- Tier 2: Confirmed memory safety bug (distinct root cause)
- Tier 3: Triggerable from external input
- Tier 4: Exploitable (could corrupt control flow)
- Tier 5: Full control-flow hijack

**Metrics**: Precision/recall against known CVEs, total unique findings, severity distribution, false positive rate, time-to-first-finding per approach.

# Proposed First Experiments

**Phase 1 — Setup & Learning (25h):** Install prerequisites (Python 3.11, Docker, Claude Code). Install Trail of Bits skills via `/plugin marketplace add trailofbits/skills`. Clone oss-fuzz-gen and add Claude Code backend class. Run each tool once on a single test project to validate they work. Security crash course with mentor: read ASan reports, learn memory safety bug classes (buffer overflow, use-after-free, integer overflow, null deref).

**Phase 2 — Experiment Design (15h):** Curate 10-15 OSS-Fuzz projects with known CVEs as ground truth. For each CVE, document the vulnerable file, function, bug class, and severity. Build the file prioritization skill/script. Design the custom composite approach. Define evaluation protocol: how to run each tool, what to record, how to measure success.

**Phase 3 — Run Experiments (35h):** Run all 6 approaches across the selected projects. For each run, record: findings (file, line, bug description), whether it matches a known CVE, false positives, time taken. For oss-fuzz-gen runs, also record build success rate, crash count, and coverage. Classify findings on the 5-tier severity scale with mentor guidance (tiers 1-2 are automatic via ASan).

**Phase 4 — Analysis (20h):** Compare approaches head-to-head. Key questions: Which tool finds the most known CVEs? Which has the lowest false positive rate? Does file prioritization improve results when added to other approaches? Does the composite outperform individual tools? What bug classes are easiest/hardest for each approach? Generate visualizations and comparison tables.

**Phase 5 — Blog Post (25h):** Communicate findings. Structure: motivation (many LLM security tools exist — which actually work?), methodology (ground-truth CVE benchmarking), results (tool comparison with clear metrics), implications for AI safety (scaffold-dependent capability amplification — do better tools meaningfully increase dangerous capabilities?), practical recommendations (which tools to use for defensive auditing), limitations.

# Theory Of Impact Chain

1. Anthropic's Mythos Preview demonstrated that advanced AI can discover thousands of zero-day vulnerabilities autonomously — a clear dangerous capability. Meanwhile, multiple organizations (Trail of Bits, Google, OpenAI) are releasing open-source tools that scaffold LLMs for security analysis.
2. A critical question for AI safety is: **how much do these readily available tools amplify an LLM's vulnerability-finding capability?** If off-the-shelf tools dramatically increase effectiveness, the barrier to using LLMs for offensive security is lower than model capabilities alone would suggest.
3. This research directly measures tool-dependent capability amplification by holding the model constant (Opus 4.6) and comparing real, publicly available tools → producing quantitative evidence on how much scaffolding matters in practice.
4. This evidence informs dangerous capability evaluations: labs and policymakers need to know whether to focus risk assessments on model capabilities alone or on the model + available tooling ecosystem.
5. The finding also has practical defensive value: a rigorous comparison of existing tools helps defenders choose the most effective approach for proactive security auditing.

# Strength Rationale

- **High safety relevance**: Directly measures how off-the-shelf tools amplify dangerous capabilities — a key input for risk assessment.
- **Practically grounded**: Compares tools people actually use (Trail of Bits skills, oss-fuzz-gen), not hypothetical scaffolding variations.
- **Clear methodology**: Controlled experiment with known ground truth (CVEs), automated verification (ASan), and reproducible tool configurations.
- **Novel angle**: No published work systematically benchmarks the ecosystem of available LLM security tools against each other on a common ground-truth dataset. Existing work (ISSTA 2024) compares prompt templates, not real tools.
- **Feasible for Ivan (120h)**: Most tools are install-and-run. The main implementation work is the oss-fuzz-gen Claude Code backend, the file prioritization script, and the composite approach. Security concepts are supported by ASan automation and mentor guidance.
- **Publishable and useful**: The results are immediately actionable — both for the safety community (capability assessment) and for practitioners (tool selection).
