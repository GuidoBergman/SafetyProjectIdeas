# Intrusion Detection CUSUM Transfer: Applying Sequential Change-Point Detection to AI Agent Monitoring

# Research Question

Current AI agent monitors use LLMs to judge whether an agent's actions are suspicious — but these are expensive and can themselves be fooled. Could a much simpler approach work as a cheap first line of defense?

We test CUSUM (cumulative sum), a lightweight statistical alarm from industrial quality control, on AI agent behavior. CUSUM learns what "normal" tool-usage patterns look like, then keeps a running tally of deviations. When the tally crosses a threshold, it fires. The core question is: **which kinds of sabotage strategies change an agent's observable tool-call patterns enough for a simple statistical method to catch, and which don't?** The answer maps out exactly where cheap monitoring helps and where you need more expensive semantic understanding — a characterization the safety field currently lacks.

# Approach Outline

AI agents act by calling tools — searching the web, writing files, sending emails, etc. We use a public dataset (ScaleAI/mrt on HuggingFace, ~9.6 GB) that recorded thousands of such agent sessions. In some sessions the agent behaves normally; in others it was secretly instructed to sabotage its task while appearing helpful. Every tool call is logged, so we have a complete record of what each agent did, step by step.

**Step 1 — Get the data and extract features (Python + pandas):**
Download the ScaleAI/mrt dataset from HuggingFace (`datasets.load_dataset("ScaleAI/mrt")`). Each trajectory is a JSON file containing a list of messages with `role`, `content`, and `tool_calls` fields. Write a script that walks through each trajectory and, at every step, extracts simple numeric features: (a) how many tool calls the agent has made in the last N steps, (b) the time/steps between consecutive tool calls, (c) which tool was called (encoded as a number). The output is a table (dataframe) where each row is one step in one trajectory, and the columns are the features above plus a label: "benign" or "malicious".

**Step 2 — Learn what "normal" looks like:**
Take just the benign trajectories. Compute the average and standard deviation of each feature (e.g., "on average, the agent calls 2.3 tools per 5-step window with std 0.8"). These statistics define "normal behavior." This is basic descriptive statistics — `df.groupby(...).mean()` and `.std()`.

**Step 3 — Implement CUSUM (~10 lines of code):**
CUSUM works by keeping a running counter. At each step, it adds `(observed_value - expected_value - slack)` to the counter (the counter can't go below zero). When the counter exceeds a threshold `h`, it triggers an alarm. In Python:
```python
def cusum(values, expected, slack, threshold):
    counter, alarms = 0, []
    for i, v in enumerate(values):
        counter = max(0, counter + (v - expected) - slack)
        if counter > threshold:
            alarms.append(i)
    return alarms
```
Run this on each trajectory's feature sequence. The two parameters (`slack` and `threshold`) control sensitivity — you'll tune them in Step 4.

**Step 4 — Evaluate detection performance:**
For each malicious trajectory, check: did CUSUM trigger an alarm, and if so, how many steps *before* the actual sabotage action? Measure three things: (a) detection rate — what fraction of sabotage sessions triggered an alarm, (b) false positive rate — what fraction of benign sessions falsely triggered, (c) lead time — how early did the alarm fire. Sweep different `slack`/`threshold` values to find the best tradeoff (plot an ROC curve using `sklearn.metrics.roc_curve`).

**Step 5 — Compare against baselines and characterize the gap:**
The dataset already includes verdicts from LLM-based monitors (AI watching AI). Compare CUSUM's detection rate and false positive rate against these verdicts. Also compare against a naive baseline: flag a trajectory as suspicious if any single feature value exceeds 3 standard deviations from the mean.

**Step 6 — Analyze what CUSUM catches vs. misses per task:**
The SHADE-Arena dataset has 17 distinct task types (e.g., code writing, email handling, document editing). For each task, report whether CUSUM caught the sabotage or missed it, and by how much (lead time or miss). Present results as a simple table: task name, CUSUM detected (yes/no), lead time, LLM monitor detected (yes/no). Look at the tasks where CUSUM failed and briefly note *why* — did the agent's tool-call pattern stay the same despite sabotage? This per-task breakdown is the core deliverable: it shows concretely where cheap statistical monitoring works and where it doesn't, without requiring you to invent a new taxonomy.

# Proposed First Experiments

Experiment 1 (Data & Baseline, ~8 hours): Download the ScaleAI/mrt dataset from HuggingFace. Parse trajectory JSON files to extract tool-call sequences (tool name, timestamp/step index) from benign runs. Compute baseline statistics: tool-call frequency distribution, inter-call intervals, tool-type transition rates. Visualize distributions to identify promising CUSUM features.

Experiment 2 (CUSUM Detection, ~12 hours): Implement CUSUM on the most discriminative features from Experiment 1. Run on held-out benign trajectories to calibrate threshold (target false positive rate). Run on malicious trajectories and measure: (a) detection rate, (b) false positive rate, (c) detection lead time — how many steps before the sabotage action does CUSUM trigger? Compare against a simple static threshold monitor on the same features, and against the LLM monitor verdicts already in the dataset.

Experiment 3 (Per-Task Analysis, ~10 hours): Break down CUSUM results by each of the 17 SHADE-Arena task types. Build a results table: task name, CUSUM detection rate, lead time, LLM monitor detection rate. For tasks where CUSUM fails, briefly examine why (e.g., tool-call pattern didn't change). Test CUSUM parameter sensitivity (slack k, threshold h) to check if per-task tuning helps.

Future Experiment (Cross-Dataset Validation): Apply the CUSUM detector trained on ScaleAI/mrt to the ATBench dataset (HuggingFace: AI45Research/ATBench, 500 trajectories with 250 safe / 250 unsafe, fine-grained safety taxonomy across 8 risk categories and 14 failure modes). This tests whether CUSUM generalizes across different agent environments and tool distributions, and the rich ATBench annotations enable analysis of which risk categories CUSUM is most/least effective at detecting.

# Theory of Impact Chain

As AI agents are given more autonomy, we need ways to catch them misbehaving. Current monitors use LLMs — expensive and slow. A cheap statistical tripwire like CUSUM could complement them, but only for certain kinds of sabotage.

The real value of this project is a **per-task breakdown**: for each of the 17 SHADE-Arena tasks, does CUSUM catch the sabotage or not? This concretely shows where cheap statistical monitoring adds value and where it fails — without requiring the researcher to invent new categories. The results directly inform how monitoring stacks should be designed.
