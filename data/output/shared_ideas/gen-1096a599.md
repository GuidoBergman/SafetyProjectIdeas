# Does knowing how evals work make models safer or just better at passing?

**TL;DR:** Finetuning models on documents describing how safety evaluations are built makes them score much safer, but no deployment-like condition was ever run. This builds matched deployment twins for those benchmarks and measures the gap the original could not.

## Guido's comments

**Title:** Does knowing how evals work make models safer or just better at passing?

## Research Question

When a model is finetuned on documents describing how safety evaluations are designed and its benchmark safety scores rise sharply, does its behaviour on a matched deployment-realistic version of the same requests improve by the same amount?

## Why This Matters

**The failure this targets:** Every evaluations-based safety case assumes benchmark behaviour predicts deployment behaviour. Documents describing how safety evaluations are built are ordinary web content, so any model trained on a web-scale corpus has some of this knowledge. If that knowledge raises benchmark scores without changing deployment behaviour, then pretraining-corpus contamination with evaluation-design documentation is a contamination pathway that inflates published safety numbers, and it is invisible to anyone who only runs the benchmark.

**Why the work reduces it:** The source work released its adapters and models but never ran a deployment-like condition, so the eval-minus-deployment gap was never measured. Building a matched twin for each benchmark, same request and same harm but stripped of the structural traits the finetuning documents describe, isolates exactly that gap. Tracking whether the over-refusal increase also transfers to the twin separates blanket caution, which would be a real if blunt safety gain, from targeted test-passing, which is not.

**Where the chain ends:** An auditor decides whether to run a deployment twin alongside any benchmark whose score they intend to cite, and whether to treat a high safety score from a model with likely evaluation-design knowledge as evidence at all.

## Day-1 Check

Download the released meta-knowledge adapter and its base model, run 100 AgentHarm items as published, then run the same 100 items with the multiple-choice scaffolding and benchmark-style system prompt removed. Report the refusal rate in both conditions. The gap between those two numbers is the first estimate of the effect, obtained in one afternoon from released artefacts.

## Approach

Take the released adapters and models from the source work and build a matched deployment-realistic twin for each of the five safety benchmarks it used: the same underlying request and the same harm, but stripped of the structural traits the finetuning documents describe, so no multiple-choice scaffolding, no synthetic tool stubs, no benchmark-style system prompt, and the request embedded in realistic multi-turn agentic traffic. Measure the eval-minus-deployment behaviour gap for the meta-knowledge models, for control finetunes trained on matched non-evaluation documents, and for the base models. A gap near zero supports genuine caution, and a large gap identifies evaluation meta-knowledge as a contamination pathway. Also track whether the reported rise in over-refusal transfers to the twin, since blanket caution should transfer and targeted test-passing should not. Ship the twins as drop-in tasks in a public evaluation framework so an auditor can run them without rebuilding anything.

## Scope and Deliverables

Stage 1, weeks 1 to 7, roughly 380 person-hours: build the deployment twin for one benchmark, validate that it preserves the request and the harm, and measure the gap for the meta-knowledge model, the control finetune and the base model. That single benchmark's gap is the headline number and a complete first result. If the twin cannot be built without changing what the benchmark measures, the project stops here and reports what makes these benchmarks untwinnable. Stage 2, weeks 9 to 17, roughly 500 person-hours: build the remaining four twins, run the full three-way comparison, and measure over-refusal transfer. Stage 3, weeks 18 to 24, roughly 420 person-hours: package the twins as drop-in evaluation tasks, release them, and write up. Final artefacts: five deployment-realistic benchmark twins released as runnable tasks, the eval-minus-deployment gap table across model conditions, the over-refusal transfer result, and a paper-quality report.

## Experiments

- Build and validate one twin. Take a safety benchmark and produce a deployment-realistic version that preserves the request and the harmful action while removing benchmark structure. Validate preservation with a judge model and human spot checks, and validate realism with a detectability discriminator against public traffic. Expected outcome: a twin that scores measurably closer to real traffic while a human rater agrees it asks for the same thing.
- Measure the three-way gap. Run the meta-knowledge model, a control finetune and the base model on both the original and the twin. Measure refusal rate and harmful-action rate in all six cells. Expected outcome: the meta-knowledge model shows a much larger eval-minus-deployment gap than the control, which is the contamination result.
- Test over-refusal transfer. Measure over-refusal on benign requests in both the original and twin formats for all three model conditions. Expected outcome: if the over-refusal rise appears only in the benchmark format, the model learned to pass tests rather than to be cautious, which is the sharpest version of the finding.

## Risks

**The twin does not preserve the harm**
- Consequence: A lower harmful-action rate on the twin is caused by the request becoming easier to refuse or harder to comply with, not by the model behaving differently, so the gap is an artefact.
- Detected by: The preservation check in experiment 1: judge-model and human agreement that the twin asks for the same thing, plus matched base-model behaviour on twin and original.
- Response: Mitigate by requiring base-model behaviour to match within a stated tolerance across twin and original before any twin enters the analysis, and reporting the base-model match as a published property of each twin.

**The released artefacts do not reproduce the source result**
- Consequence: The gap is being measured on models that do not show the effect the project is about, so no conclusion can be drawn.
- Detected by: Reproduce the source work's reported benchmark score changes on its own benchmarks in week 1 and compare against published values within a stated tolerance.
- Response: Retry by refinetuning from the described document corpus, and if the effect still does not appear, publish the failed replication, which is itself a substantive result about a recent claim.

**The control finetune is not matched**
- Consequence: Any gap difference could come from finetuning on any document corpus rather than from evaluation-design knowledge specifically.
- Detected by: Compare the control's benchmark score change against the meta-knowledge model's, and check that both finetunes match on token count, document length distribution and training steps.
- Response: Mitigate by matching the control corpus on those properties and on topic breadth, and reporting the control's own gap as the baseline that the meta-knowledge gap must exceed.

**Twins are only realistic relative to our own judgement**
- Consequence: The deployment condition is another constructed condition, so the measured gap is between two artificial distributions.
- Detected by: Score each twin's detectability against public traffic corpora with a discriminator panel and report the AUROC alongside every result.
- Response: Mitigate by publishing each twin's detectability score as a stated property, so the gap is explicitly reported as conditional on how realistic the twin measurably is.

## Prerequisites

- The released adapters, models and finetuning document corpus from the source work
- The five safety benchmarks it used, plus public traffic corpora for realism scoring
- GPU access for running five benchmarks in two formats across three model conditions, plus a modest API budget for judge scoring
- A judge model and human spot-check protocol for harm preservation
- Familiarity with evaluation-harness construction, adapter loading and detectability scoring

## Who This Is For

Third-party auditors who cite public safety benchmark scores, concretely METR and the UK AI Safety Institute pre-deployment testing team. Today they run public benchmarks in their published format and report the resulting scores. With this, they would run the released deployment twin alongside the original for any benchmark they intend to cite, and report the pair of scores rather than the benchmark score alone.

## Open Questions

- How much evaluation-design knowledge does an ordinary web-scale pretraining corpus already contain, and can that be estimated without access to the corpus?
- If the gap is large, is the right response to build twins for every benchmark, or to change how benchmarks are structured so evaluation-design knowledge does not help?
- Does the effect scale with model capability, so that stronger models exploit the same knowledge more?
- Can a deployment twin ever be validated as deployment-like without access to real deployment traffic?
